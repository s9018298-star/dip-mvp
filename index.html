◆ IAM·09 · SUPER_ADMIN BOUNDARY ◆

SUPER_ADMIN 身分邊界

DI 內部全域管理身分 — 但不是「後門」，走的是一般授權路徑

🛡
IAM_ADMIN 一般管理者
  • Organization 管理：有權限的 Org
  • Project 管理：依 Org 繼承規則
  • User List：有權限的 Scope
  • 查看 User Status：有權限的 Scope
  • Invite / Role Binding：有權限的 Scope
  • Effective Access / Audit：有權限的 Scope
  • Disable User（不允許）
  • Enable User（不允許）
⚡
SUPER_ADMIN DI 全域
  • Organization 管理：所有 Org
  • Project 管理：所有 Project
  • User List：全平台
  • 查看 User Status：全平台
  • Invite / Role Binding：全平台
  • Effective Access / Audit：全平台
  • Disable User（允許）
  • Enable User（允許）
💡 關鍵設計哲學：沒有授權後門。
SUPER_ADMIN 不走 PDP / SpiceDB 全域繞過，而是在每個 Organization 都要有 iam_admin binding — 和一般 admin 走同一條授權路徑。
▸ 建立 SUPER_ADMIN → 自動為其建立所有現有 Org 的 iam_admin Binding
▸ 新增 Organization → 自動為所有有效 SUPER_ADMIN 補該 Org 的 Binding
▸ 移除 SUPER_ADMIN → 撤銷其所有 Org Binding + 撤銷全域管理身分
🔐 對客戶可以這樣講：DI 內部人員也沒有「隱形的 root 權限」，所有操作都會留下 iam_admin 的 Binding 紀錄 + Audit Log — 可查、可撤銷、可稽核。

Subject ID Contract

IAM 授權識別統一使用 Canonical Subject ID — 跟 Keycloak UUID 分離

👤
USER
usr_...
一般使用者帳號 · 可來自 Keycloak / LDAP / SSO · 授權查詢統一用這個 ID
👥
GROUP
grp_...
使用者群組 · 把相同角色的 user 歸成一組 · 對 group 授權會繼承到成員
🤖
SERVICE ACCOUNT
svc_...
機器對機器 · 跑 batch / 呼 API 的身分 · 下游產品統一用 Service Account 存取
💡 設計哲學：授權資料跟 IdP 解耦。
JWT.sub 維持 Keycloak UUID（身分解析），但 IAM 授權查詢 / SpiceDB Relation / Audit Log 一律用 usr_ / grp_ / svc_ 開頭的 Canonical ID。
▸ 換掉 IdP（Keycloak → Auth0 / Okta）→ 只要做 UUID 對應，授權資料完全不動
▸ 不得以 Email / Username / Keycloak UUID 代替 Subject ID
