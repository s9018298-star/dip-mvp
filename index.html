◆ IAM·09 · SUPER_ADMIN BOUNDARY ◆👥 Who

SUPER_ADMIN 身分邊界

DI 內部全域管理身分 — 但不是「後門」，走的是一般授權路徑

🛡
IAM_ADMIN 一般管理者
  • Organization 管理：有權限的 Org
  • Project 管理：依 Org 繼承規則
  • User List：有權限的 Scope
  • 查看 User Status：有權限的 Scope
  • Invite / Role Binding：有權限的 Scope
  • Effective Access / Audit：有權限的 Scope
  • Disable User（不允許）
  • Enable User（不允許）
⚡
SUPER_ADMIN DI 全域
  • Organization 管理：所有 Org
  • Project 管理：所有 Project
  • User List：全平台
  • 查看 User Status：全平台
  • Invite / Role Binding：全平台
  • Effective Access / Audit：全平台
  • Disable User（允許）
  • Enable User（允許）
💡 關鍵設計哲學：沒有授權後門。
SUPER_ADMIN 不走 PDP / SpiceDB 全域繞過，而是在每個 Organization 都要有 iam_admin binding — 和一般 admin 走同一條授權路徑。
▸ 建立 SUPER_ADMIN → 自動為其建立所有現有 Org 的 iam_admin Binding
▸ 新增 Organization → 自動為所有有效 SUPER_ADMIN 補該 Org 的 Binding
▸ 移除 SUPER_ADMIN → 撤銷其所有 Org Binding + 撤銷全域管理身分
🔐 對客戶可以這樣講：DI 內部人員也沒有「隱形的 root 權限」，所有操作都會留下 iam_admin 的 Binding 紀錄 + Audit Log — 可查、可撤銷、可稽核。

👤

ADR-DBRG-001

ADR-DBRG-002
2026-09-06
📝 Data Contract → Schema（命名變更）

Data Contract 更名為 Schema · 因為易用性測試發現大多數人無法直接將 Schema 和 Data Contract 做聯想

💡 設計原則：命名要符合使用者心智模型 · 不要用工程師自嗨的術語當 UI 文字
ADR-DBRG-003
2026-10-21
🏷 Topic Type → Classifications（屬性疊加）

Topic 的 type 改成 Classifications · 變成屬性疊加概念（而非單選）· MVP 只有 Event 一種

💡 為什麼：未來要支援多種分類（Event / Live / Metric...）同時掛在一個 Topic 上，一開始就用 array 設計
ADR-DBRG-004
2026
🔐 Compatibility Mode: Backward → FULL

Schema 相容性模式由 Backward 改為 FULL · 採取最嚴格的相容性策略

💡 治理承諾：Schema 演化不會破壞上下游任一端 · 新舊 producer / consumer 都能繼續運作（trade-off：Schema 修改自由度降低）
ADR-DBRG-005
2026-08-24
⏳ Topic Status 新增 processing（非同步建立）

送出建立 Topic 時，Schema Registry 或 Kafka 服務可能異常 · 為避免使用者混亂，只要非 DB 儲存失敗，使用者都會看到建立成功，狀態為 processing，表示 Topic 仍在建立中

💡 UX 設計：不用紅字錯誤嚇使用者，背後讓系統 retry，狀態機處理
